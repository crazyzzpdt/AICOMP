### 处理原则

1. 保持当前划分用于旧运行/v3 可比评估。v3 已修正 Mosaic 日程与球类迁移，但最终 AP 未改善；下一步先统一评估、按场景复核弱类，不因分数低移动验证难例或删除标注。训练对比与早期球类诊断见 [训练配置与数据集复核](04_数据与调参经验.md#record-2)。
2. 如需清理 64 个边缘框、空标注或同 RGB 样本，先逐图复核并记录原标签与理由。裁边须裁剪 xyxy 后重算中心宽高，不能直接分别截断 cx/cy/w/h。原始数据不改；RGB 为硬链接，禁止原地改写像素。本次未执行清洗；如修订验证标签，须重新评估所有基线，不与旧指标直接比较。
3. 后续按真实场景组固定更有代表性的验证方案，覆盖 JPG 和稀有类；不能仅为凑类别数量拆开相邻帧。更换划分后必须重跑基线，不能与旧 0.37746 直接比较。
4. 数据增强限官方训练集，裁剪、缩放必须三模态同步且同步变换框。稀有类采样、目标裁剪列为后续单独实验，尚未启用；禁止外部扩充和使用测试标注训练。

## 4. 划分方法（防泄漏设计）

按参赛手册要求"相邻/相同场景样本不得分跨两侧"：

1. **场景组为原子单位**：前缀组 + 纯数字连续段，共 **776 组**（组大小 1~363），整组进 train 或 val，绝不拆组。
2. 每类"最小场景组"预留给 val，保证 **12 类双侧覆盖**（稀有类 boat/uav 在 val 各 3 框）。
3. 其余组按 9:1 进度贪心配平；巨型段在间隔最大处切开后再参与（最大间隔最可能是真实场景分界）。

初次划分结果：val 14 组 / train 762 组（该划分 2026-09-15 经泄漏复检修正，见第 7 节）。

## 7. 跨集泄漏复检与修正（2026-09-15）

对 240×1760 全配对做跨集近似重复扫描（96×96 灰度余弦相关 + 同类框坐标重合度双重判据），发现**纯数字 ID 是带前缀场景的重发版**，同一场景的两种命名被分到了 train 和 val 两侧。判据：余弦 >0.85 且同类框中位距离 <0.03（已确认同场景对的实测距离为 0.004~0.026，不同场景对为 0.06~0.51，区分度干净）。

确认的 5 对近重复（val 纯数字 ↔ train 带前缀）：

| val 图 | train 同场景图 | 余弦 | 框中位距离 |
|---|---|---:|---:|
| 003152 | 000006_002_00000001 | 0.992 | 0.010 |
| 003919 | 000008_047_00000149 | 0.988 | 0.006 |
| 003179 | 000006_004_00000104 | 0.972 | 0.004 |
| 002888 | 000005_011_00000421 | 0.934 | 0.010 |
| 003047 | 000005_027_00000247 | 0.922 | 0.012 |

另有 2 处：`val:000006_013_00000001` ↔ `train:003262`（余弦 0.891）；`val:000015_004_suppl_00000223` 与 `train:000015_004_*` 三帧同组（`_suppl` 后缀使分组规则把它切到了另一侧）。

**修正方式**：把上方 train 侧的**整段采集**移入 val（共 16 帧），而非只移重复帧——前缀组是同一段采集，组内相邻帧按规则同样不应跨集。移动用 `mv` 完成，硬链接不破。修正后 train 1744 / val 256，12 类双侧覆盖不变，val 的 boat 从 3 框升至 7 框。

**残留**：2026-09-15 对 val 256 × train 1744 **全枚举**余弦 >0.85 的对，共 **11 对**，逐对算双向同类框中位距离后**全部判为不同场景**（实测距离 0.036~0.512，而下方确认同场景的 5 对为 0.004~0.026，区分度干净）。余弦最高的一对是 `val:003653 ↔ train:shuming_503_00000052`（0.8948），但框距离 0.2818 / 0.1383，属相似城市场景。距离最贴近临界的是 `val:003519 ↔ train:000008_007_00000868`（0.0383 / 0.0362），如后续发现分数仍偏高，可优先核查这一对。另 `val:003982 ↔ train:000004_009_00000081` 反向距离 0.0171 系 train 图仅 1 框导致的统计假象。

**教训**：划分脚本假设「纯数字连续段 = 独立场景组」不成立——数字 ID 中存在带前缀场景的重发版。重建划分时必须把内容级近似重复并入同一场景组再切分。

| 总 epochs | 完成 150 轮后的 one-to-many / one-to-one 权重（源码计算） |
|---|---|
| 5000 | 约 0.779 / 0.221 |
| 300 | 约 0.449 / 0.551 |
| 200 | 约 0.272 / 0.728 |

这些是源码计算值，不是日志实测。5000 轮并非只影响早停上限：即使学习率已收敛，双头损失进度仍很靠前。但这不能证明它是低分原因，尤其当前验证采用 NMS 分支，改变双头比例可能有收益也可能有损害。后续可独立实验解耦损失日程，或对照有限 300 轮日程；本次未改用户的 5000 轮设置。

## 1. 结论与适用范围

v1 训练时长设置为 `epochs=1000`、`patience=100`：最多训练 1000 轮，验证指标连续 100 轮没有刷新最佳值时自动停止。旧学习率按 1000 轮规划，`close_mosaic=40` 在计划中的最后 40 轮生效；提前停止可能错过关闭 Mosaic 阶段。官方 2000 张图全部保留，其中 1744 张用于训练，256 张作为独立验证集。

当前 `datasets/` 在文件来源、配对和可加载性上有效，1744/256 的数量比例也合理，但验证集的分布代表性不足，不能据此承诺一次训练达到最优成绩。官方原始图像、标注和测试集均未修改。

2026-09-16 已收敛为单一数据集结构：`main.py` 使用 `datasets/data.yaml`，`datasets/` 下仅有 `train/`、`val/` 两个数据目录。输入为 RGB（3）+ 红外（1）+ 深度（1）共 5 通道；标签来自官方 `new_labels_2000`，并保留既有 1744/256 划分。官方旧标注仍保存在原始数据目录。

全量核验确认同名三模态尺寸一致：1851 组 PNG 均为 1920×1080，149 组 JPG 均为 640×360。此前上采样说明源于样本索引错配后的错误判断，已纠正。加载器检查同名与同尺寸，再将 RGB、红外、深度组合为五通道；几何增强同步执行，HSV 关闭。

本次代码复核修正了可见光通道顺序：框架仅对三通道图自动执行 BGR→RGB，五通道图必须在融合前自行转换。缓存随融合实现或源图更新而失效。续训通过 `main.py` 的 `RESUME_PATH` 指定五通道检查点，继续使用自定义训练器；不要使用普通 YOLO CLI 续训。训练与验证各自复制增强参数，缩小训练样本比例时仍使用完整验证集。

| workers | 4 | 实测 Windows 多进程数据加载正常，兼顾 9950X 供数能力与子进程内存 |
| cache | disk | 利用 NVMe，缓存融合后的五通道图像以减少每轮三文件解码；缓存生成在 `datasets/train` 和 `datasets/val` 内 |
| optimizer | MuSGD | 显式固定当前版本的长周期 auto 配方，lr0=0.01、momentum=0.9、warmup_bias_lr=0 |
| warmup_epochs | 5 | 为预训练模型到 12 类检测头的适配留出预热阶段 |
| nbs | 64 | 预热后每约 16 个 batch 累积更新一次；这不等同于 BatchNorm 也看到 64 张图 |
| epochs | 1000 | 为后续增加官方允许的训练数据预留训练上限；实际训练轮数同时受早停控制 |
| patience | 100 | 验证 fitness 连续 100 轮没有提高时自动停止；最终仍使用整个训练过程中保存的 `best.pt` |
| cos_lr / lrf | True / 0.01 | 按最多 1000 轮规划余弦下降；若提前停止，学习率不会走到计划末值 |
| close_mosaic | 40 | 计划在第 960 轮后关闭 Mosaic；提前停止时可能不会进入这一阶段 |
| scale | 0.3 | 缩放范围约 0.7–1.3，减少过强缩小对小目标的损害 |
| cls_pw | 0.25 | 对类别不均衡做温和逆频率加权；训练集归一化权重约 0.54–1.95，避免完整逆频率的极端权重 |
| val / conf / iou | True / 0.001 / 0.7 | 以验证 PR 曲线选权重；0.7 是 NMS 阈值，不是评测 IoU 阈值 |
| max_det | 100 | 与赛题每图最多 100 个预测框一致；当前标注最大为 66 个 |
| save_period | 25 | 除 best/last 外定期保留中间权重，便于排查或恢复 |

模型选择原则：n/s 适合速度优先，m 适合更低的显存和计算预算，l 在本机兼顾较高输入分辨率与预训练容量；x 的计算开销明显更高，其 COCO 优势不保证迁移到本赛题。官方公布的 l/m 参数和 FLOPs 是融合后的部署统计，训练网络保留双检测分支，因此实际训练时显示的参数量更高。[官方模型比较](https://docs.ultralytics.com/models/yolo26/)

历史 v1 以 1000 轮作为上限，并用 100 轮耐心值控制早停。当前 v3 已独立处理学习率与 Mosaic 日程，但 epochs 仍影响 YOLO26 双头损失日程，不能视为纯上限；详见置顶复盘。[训练参数说明](https://docs.ultralytics.com/modes/train/)

五通道短训只验证了 1280、batch=4 能稳定运行，不能准确换算 1000 轮总耗时。正式耗时应以第一个完整 epoch（包含训练和 256 张验证图）的实测时间估算；早停可能明显缩短总时长。

`main.py` 还在导入 Ultralytics 前启用离线模式、关闭自动安装，并检查本地权重与 CUDA/BF16 可用性。预训练权重来自 `orgin_models`，不加入外部训练样本。

## 4. 对既有经验文档的校正

- `auto_augment="randaugment"` 是分类任务增强，不会自动增强当前 detect 任务。
- 本版本 `optimizer="auto"` 根据估算迭代次数在 AdamW/MuSGD 之间选择，并不是始终 MuSGD。
- 本版本检测 fitness 权重为 `[0, 0, 0, 1]`，即使用 mAP50-95；旧经验中“best.pt 不一定按最高 mAP50-95 选”的概括不适用于本次安装版本的正常检测训练。
- JPG 深度图实际上是 8-bit RGB，只有 1851 张 PNG 深度图是 16-bit。以后做融合不能将全部深度文件按毫米数值统一处理。
- “框架能够加载”仅说明格式可接受，不能证明场景独立、标注正确或验证集具有代表性。

### 1.2 生成图片路径清单 txt

```python
import os

def generate_txt_for_cvat(target_dir, output_filename):
    exts = ('.jpg', '.jpeg', '.png', '.bmp')
    lines = []
    for root, _, files in os.walk(target_dir):
        for f in files:
            if f.lower().endswith(exts):
                # join 后统一转正斜杠，跨系统不踩坑
                lines.append(os.path.join(root, f).replace('\', '/'))
    with open(output_filename, 'w', encoding='utf-8') as f:
        f.write('\n'.join(lines) + '\n')
    print(f"已记录 {len(lines)} 条路径 -> {output_filename}")
```

### 1.3 images/labels 配对清洗（训练前必做）

按文件名词干检查图片与标注是否成对，只能发现缺图、缺标注等结构问题。框位置、类别语义、漏标、同场景泄漏需要进一步核验；不要未经检查就删除不配对样本。

```python
import os, shutil

def collect_matched_data(image_dir, label_dir, output_dir):
    os.makedirs(output_dir, exist_ok=True)
    exts = ('.jpg', '.jpeg', '.png', '.bmp', '.webp')
    image_dict = {os.path.splitext(f)[0]: f
                  for f in os.listdir(image_dir) if f.lower().endswith(exts)}
    count = 0
    for f in os.listdir(label_dir):
        key = os.path.splitext(f)[0]
        if f.lower().endswith('.txt') and key in image_dict:
            img = image_dict[key]
            shutil.copy(os.path.join(image_dir, img), os.path.join(output_dir, img))
            shutil.copy(os.path.join(label_dir, f), os.path.join(output_dir, f))
            count += 1
    print(f"配对成功并复制 {count} 对 -> {output_dir}")
```

### 1.4 批量统一类别 id（合并多数据集第一步）

不同来源数据集的类别编号体系不同，合并前把标注第一列统一成目标索引：

```python
import os

def unify_class_ids(label_dirs, class_id='0'):
    for folder in label_dirs:
        if not os.path.exists(folder):
            continue
        for name in os.listdir(folder):
            if not name.endswith('.txt'):
                continue
            path = os.path.join(folder, name)
            with open(path, 'r') as f:
                lines = f.readlines()
            with open(path, 'w') as f:
                for line in lines:
                    parts = line.split()
                    if parts:
                        parts[0] = class_id          # 强行统一类别索引
                        f.write(' '.join(parts) + '\n')
```

### 1.5 视频抽帧造数据

每秒抽 1 帧（`frame_count % fps == 0`）即可——相邻帧高度冗余，抽更密意义不大：

```python
import cv2, os

def extract_frames(video_path, output_dir):
    os.makedirs(output_dir, exist_ok=True)
    cap = cv2.VideoCapture(video_path)
    if not cap.isOpened():
        print(f"无法打开: {video_path}"); return
    fps = int(round(cap.get(cv2.CAP_PROP_FPS)))
    total = int(cap.get(cv2.CAP_PROP_FRAME_COUNT))
    print(f"总帧数 {total}，帧率 {fps} FPS，约抽 {total // fps} 张")
    i = saved = 0
    while True:
        ret, frame = cap.read()
        if not ret:
            break
        if i % fps == 0:
            saved += 1
            cv2.imwrite(os.path.join(output_dir, f"{saved}.png"), frame)
        i += 1
    cap.release()
    print(f"完成，共 {saved} 张 -> {output_dir}")
```

### 1.7 数据配比与划分经验

1. **负样本占 5%~10%**：混入"什么都不是"的背景图，明显压误检。实例：火灾项目靠 5% 负样本防止把太阳、灯光识别成火源；打架项目的 normal 类同理。
2. **验证集 10%~20% 就够**：实例教训——火灾项目把 33% 数据分去验证了，浪费训练数据。
3. **类别索引与 yaml 严格对齐**：不同项目索引顺序可以不同（火灾 `0:normal,1:fire`，打架 `0:fight,1:normal`），但**同一项目内一经训练就固定**，中途调换/增删 = 作废重来。
4. **空 txt 是合法标注**：代表纯背景负样本图，别当垃圾清掉；用 1.3 的配对逻辑保持图-标一一对应。
5. **合并后用计数核对**：实际图片数应等于标注数；与计划量对不上且等比缩减，说明合并时删过样本——要能说清删了什么。实例：打架项目计划 31680/4746/2326，实际入库 25878/3697/1849。

### 2.2 接入 CVAT 云端自动标注

思路：本地模型包装成 `DetectionFunctionSpec` → cvat-sdk 对指定 Job 批量预标注：

```python
from cvat_sdk.core.client import Client
from cvat_sdk.auto_annotation.functions import annotate_job
from cvat_sdk.auto_annotation.interface import (DetectionFunctionSpec,
                                                label_spec, rectangle)
from ultralytics import YOLO
import PIL.Image

model = YOLO("./runs/detect/train/weights/best.pt")
spec = DetectionFunctionSpec(labels=[label_spec(n, i) for i, n in model.names.items()])

def detect(context, image: PIL.Image.Image):
    results = model.predict(source=image, verbose=False)
    for r in results:
        if r.boxes is not None:
            for box, cls in zip(r.boxes.xyxy, r.boxes.cls):
                yield rectangle(int(cls.item()), [p.item() for p in box])

with Client(url="https://app.cvat.ai") as client:
    client.api_client.configuration.api_key["TokenAuth"] = API_KEY     # 从环境变量取
    client.api_client.configuration.api_key_prefix["TokenAuth"] = "Token"
    annotate_job(client, JOB_ID, func=detect, spec=spec, allow_unmatched_labels=True)
```

> 续训从最近成功保存的轮次恢复，不恢复中断轮中尚未保存的批次；同时恢复检查点训练参数和优化器。更换配方应新开运行，不能假设传入的所有参数都会覆盖 resume 配置。本项目使用 `main.py` 的 RESUME_PATH 分支。

### 3.3 导出

```python
model.export(format="engine")   # TensorRT；也支持 onnx / openvino / tflite / onnx
```

### 3.4 性能与显存经验（5080 16G 实测基线）

- **batch 从小往上试**：imgsz=640、yolo26n 时 5080 能吃 batch=78（显存 ~14G）。爆 OOM 就减半回退。
- **速度参考**：n 模型 640 分辨率、batch=78 时约 966 batch/epoch ≈ 4 分钟，验证 3915 张 ≈ 29 秒。换算自己的数据量估算时长。
- **cache**：内存富余 `cache=True` 最快；不够用 `cache="disk"` 也比每次读盘强；数据在机械盘就别开。
- **workers**：Windows 下 2~6 都行，太大会卡在进程创建。
- **优化器**：当前安装版本的 auto 会按训练迭代数选择 AdamW 或 MuSGD；项目显式设置 AdamW，不由 auto 决定。
- **增强**：auto_augment=randaugment 用于分类，不会增强本项目 detect。五通道几何增强必须同步，不能直接对五通道使用 RGB HSV。

## 5. 踩坑速查表

| 坑 | 现象 / 原因 | 解法 |
|---|---|---|
| Windows 多进程报错 | DataLoader 递归创建进程 | 训练代码包进 `if __name__ == '__main__':` |
| device 编号对不上 | 任务管理器里核显是 0，torch 里不是 | torch 里独立显卡优先；写 `device=0` 前先确认 |

| 类别顺序错乱 | 训练后调换 names 顺序 | 一经训练索引即固定；要改就重标或做映射脚本 |
| 图标不配对 | 缺标注或缺图片 | 训练前跑 1.3 配对清洗 + 计数核对 |

## 1. 标准目录结构

```text
<dataset_name>/                      # 数据集根目录，与 yaml 同名
├── <dataset_name>.yaml              # 数据集配置文件
├── 数据分配.txt                      # 数据来源与划分记录（自用备注，非必需）
├── train/
│   ├── images/                      # 训练集图片
│   ├── labels/                      # 训练集标注（YOLO txt）
│   └── labels.cache                 # Ultralytics 首次训练自动生成（可删，会重建）
├── val/
│   ├── images/
│   ├── labels/
│   └── labels.cache
└── test/
    ├── images/
    └── labels/
```

要点：

1. `train / val / test` 三级划分；`test` 可选，最少保留 `train + val`。
2. 每个划分下 `images/` 与 `labels/` 平级、**同名配对**：`images/xxx.jpg` ↔ `labels/xxx.txt`（仅扩展名不同）。
3. `labels.cache` 是首次训练时由 Ultralytics 生成的标签缓存，用于加速后续训练；删除后下次训练自动重建。
4. 配置文件可自行命名，训练时传入对应 YAML 路径；本项目命名为 `datasets/data.yaml`。

## 2. 数据集配置文件（yaml）

实例 `fight_detector.yaml`：

```yaml
train: ./train/images
val: ./val/images
test: ./test/images
# 类别名称
names:
  0: fight
  1: normal
```

说明：

- **不要写 `path:` 键**，只写 `train / val / test` 的相对路径即可。Ultralytics 取基准目录的顺序是
  `extract_dir → yaml 的 path 键 → yaml 所在目录`（`data/utils.py: check_det_dataset`），只有前两者都取不到时才用 yaml 所在目录。
  一旦写了 `path:`，其值会被**原样使用**，并**不**相对 yaml 解析；仅当该路径不存在且是相对路径时，才回退到全局设置 `datasets_dir`（见 `yolo settings`）。
- 由此产生最典型的坑是 `path: .`：`.` 恒为「存在」，不会触发回退，基准于是落在**当前工作目录**上，
  训练时报 `Dataset 'xxx.yaml' images not found`。2026-09-15 本项目 `datasets/data.yaml` 即踩此坑（已删除该行）。
- 确需显式指定基准时写**绝对路径**；相对路径（含 `.`、`./datasets`）的语义会随 CWD 与 `datasets_dir` 漂移，不要依赖。
- `names` 用 `类别索引: 类别名`，索引与标注 txt 中每行第一个数字对应。
- 类别索引从 0 开始；类别顺序一经训练就固定，不要中途调换或增删。
- 只需训练/验证时可省略 `test:` 一行。

## 3. 标注格式（YOLO txt）

每张图片对应一个同名 txt，每行一个目标框：

```text
<class_id> <x_center> <y_center> <width> <height>
```

- 坐标与宽高均为 0~1 归一化值（相对整图，非像素）。
- `class_id` 即 yaml `names` 中的索引。
- 无目标的图片允许空 txt（作为负样本参与训练）。

## 划分规则

1. **同场景必须整组进同一侧**。划分单位不是单张图，是"场景组"：文件名前缀组（`000006_010_帧号`、`shuming_985_帧号`）+ 纯数字连续段（ID 间隔 >50 视为断界）。同场景跨集会直接让 val 分数虚高，参赛手册明令禁止。
2. **每类最小场景组预先留给 val**，保证 12 类双侧都有框。否则稀有类在 val 归零，那一类的 mAP 就永远测不出来。
3. **判同场景必须看内容，不能只看文件名**。本数据集踩过的坑：纯数字 ID 里混着带前缀场景的**重发版**，同一场景两种命名，按文件名分组会把它们切到两侧。初次划分 240 张 val 里有 6 张与 train 同场景（余弦相似度 0.92~0.99、框坐标重合），已按整段采集迁回 val 侧修正。
4. **判据用双指标**：96×96 灰度余弦相似度 >0.85，且同类框中位距离 <0.03。实测同场景对的距离是 0.004~0.026，不同场景对是 0.06~0.51，分开得很干净。只靠相似度会被相似的城市场景骗（0.85~0.89 那一带全是不同场景）。
5. **校验集比例**取 ~13%，落在通用经验 10%~20% 内。宁可 val 稍大：这份数据 scene 差异大，val 太小则指标抖动盖过改进幅度。

## 与通用经验的对照

- 新版有 1 个空标注，尚未逐图确认是否纯背景；不能为凑负样本比例删除真实目标框。
- 三模态与标签来源一致、类别齐全，不等于无标注瑕疵。已记录 5 行原始值略超 1、1 行重复，以及排除舍入误差后的 64 个边缘越界框；边缘框需逐图复核，不能直接批量删除。
- ball 验证 12 个框已逐框检查位置；AP=0 尚不能归因于唯一因素。当前验证集缺少全部 149 张低分辨率 JPG，稀有类场景少，需要后续固定更有代表性的验证方案。
- 增强、类别加权与采样须分别做对照；提高推理 conf 不保证提高 mAP，过高会丢失候选框。
